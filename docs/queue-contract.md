# Queue Contract

[Repository](../README.md) · **Queue Contract** · [Core Queue Engine](core-queue-engine.md)

This document defines Queuemaxxing's externally observable behavior. The implementation and tests must conform to it.

## 1. Queues and Messages

Each queue has a unique name and one immutable ordering mode: `fifo` or `lifo`.

| Field | Rule |
| --- | --- |
| Queue name | 1–64 characters matching `[a-z0-9][a-z0-9_-]{0,63}` |
| Ordering | Required at creation; must be `fifo` or `lifo` |
| Message ID | Opaque and generated by the server |
| Body | Valid, non-empty UTF-8; maximum 256 KiB |
| Priority | Signed 32-bit integer; defaults to `0`; higher values rank first |
| Sequence | Monotonically increasing unsigned 64-bit integer scoped to the queue |
| Delay | Integer from `0` to `900` seconds; defaults to `0` |
| Timestamps | Server-generated UTC timestamps encoded as RFC 3339 |

Queue configuration cannot be changed after creation. Sequence numbers are never reused, and exhaustion fails rather than wrapping to zero.

## 2. Ordering and Delay

Only eligible messages participate in dequeue ordering:

1. Higher priority wins.
2. Equal-priority FIFO queues choose the lower sequence.
3. Equal-priority LIFO queues choose the higher sequence.

```text
FIFO: A(p5), B(p10), C(p5) → B, A, C
LIFO: A(p5), B(p10), C(p5) → B, C, A
```

Availability is calculated once during enqueue:

```text
available_at = created_at + delay
```

A message becomes eligible when `available_at <= dequeue_time`. Until then, it does not participate in ordering, even if it has the highest priority. Once eligible, it retains its original priority and sequence.

Before selecting a message, dequeue promotes all eligible delayed messages into the ready heap. Correctness does not depend on a background scheduler.

## 3. Delivery and Concurrency

Dequeue is destructive and provides at-most-once delivery:

- A successful dequeue permanently removes and returns the selected message.
- An empty queue returns `204 No Content` through the HTTP API.
- There are no leases, acknowledgements, or automatic retries.
- If the server commits a dequeue but crashes before responding, the message remains removed.

Operations are atomic within each queue:

- Concurrent enqueues receive unique, increasing sequences.
- Concurrent dequeues cannot return the same message.
- Different queues may operate concurrently and have independent sequence spaces.
- No ordering guarantee exists across queues.

Exactly one server process may own a data directory. A second process must fail instead of risking corruption.

## 4. Durability and Recovery

Create, enqueue, and dequeue succeed only after their Write-Ahead Log record is synced to disk:

```text
lock → append WAL record → sync → update memory → unlock → respond
```

If append or sync fails, the operation returns an error and does not modify memory.

On startup, WAL replay reconstructs queue definitions, undequeued messages, ready/delayed membership, and the next sequence number.

- An incomplete final record is treated as an interrupted write and may be ignored or truncated.
- A complete record with an invalid checksum is corruption and stops startup.
- Interior corruption must never be silently skipped.

Durability covers acknowledged operations on one machine after a successful filesystem sync. It does not cover loss or failure of the underlying machine or storage device.

## 5. Validation and Errors

Invalid operations never change durable or in-memory state.

| Condition | HTTP result |
| --- | --- |
| Invalid queue name, ordering, body, priority, or delay | `400 Bad Request` |
| Queue already exists | `409 Conflict` |
| Queue does not exist | `404 Not Found` |
| No eligible message | `204 No Content` |
| WAL append or sync failure | `500 Internal Server Error` |

Errors use a stable JSON shape:

```json
{
  "error": {
    "code": "invalid_delay",
    "message": "delay_seconds must be between 0 and 900"
  }
}
```

## 6. Acceptance Cases

| Queue | Enqueued messages | Expected dequeue order |
| --- | --- | --- |
| FIFO | `A, B, C` | `A, B, C` |
| LIFO | `A, B, C` | `C, B, A` |
| Priority + FIFO | `A(p5), B(p10), C(p5)` | `B, A, C` |
| Priority + LIFO | `A(p5), B(p10), C(p5)` | `B, C, A` |
| Delay + Priority + FIFO | `A(p10,d10), B(p1,d0), C(p10,d10)` | `B`, then `A, C` once eligible |
| Delay + Priority + LIFO | `A(p10,d10), B(p1,d0), C(p10,d10)` | `B`, then `C, A` once eligible |

Tests must also verify the exact availability boundary, unique concurrent dequeues, restart recovery, and truncated-tail recovery.

## First-Version Non-Goals

- ACK/NACK, visibility timeouts, retries, and dead-letter queues
- Blocking dequeue or long polling
- Pub/Sub fan-out
- Replication, clustering, or shared multi-process storage
- WAL snapshots and compaction
- Authentication, tenant isolation, capacity limits, and backpressure
